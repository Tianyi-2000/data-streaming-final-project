# DATA_SOURCE.md

## Overview
Our pipeline uses a **hybrid data model**:

1. **Catalog metadata — real**, pulled once from the **MusicBrainz** open music
   encyclopedia (real recording/artist IDs, titles, and durations).
2. **Play events — synthetic**, generated by our own code on top of that real
   catalog to simulate listening behavior, including deliberate streaming-fraud
   patterns that do not exist in any public dataset.

This separation is intentional: the *catalog* is real and citable, while the
*listening behavior* is simulated because real per-user streaming logs are
private and not publicly available.

---

## Source
| Field | Value |
|---|---|
| **Source** | MusicBrainz (open music metadata database) |
| **Owner / maintainer** | MetaBrainz Foundation |
| **Link** | https://musicbrainz.org — API: https://musicbrainz.org/doc/MusicBrainz_API |
| **Access method** | Public REST API (`https://musicbrainz.org/ws/2`), no API key required |
| **How we access it** | `src/fetch_musicbrainz_catalog.py`, run **once** to cache results |

## Access rules & rights
- **No account or API key** is required for the public API.
- **Rate limit:** ~1 request/second. A descriptive **User-Agent with a contact**
  is required. Our fetch script enforces both (a `--contact` argument fills the
  User-Agent; requests are throttled to ~1/sec).
- **Licensing:** MusicBrainz **core data** (artists, recordings, titles,
  durations — exactly what we use) is released into the **public domain (CC0)**.
  This makes the cached IDs and durations free to redistribute in this repo.
- We store only the fields we need (IDs, title, duration, artist name); we do
  not scrape or redistribute any restricted/supplementary MusicBrainz data.

## Schema (fields we cache)
`data/catalog.json`:
```json
{
  "source": "musicbrainz",
  "artist_count": 57,
  "track_count": 500,
  "tracks": [
    {
      "track_id": "<MusicBrainz recording MBID>",
      "artist_id": "<MusicBrainz artist MBID>",
      "artist_name": "Radiohead",
      "title": "Karma Police",
      "track_duration_seconds": 261
    }
  ]
}
```
These `track_id` / `artist_id` values are used verbatim in every generated
`PlayEventV1` event, so the event stream is grounded in real music IDs.

## Limitations
- MusicBrainz stores recording length in **milliseconds and it is sometimes
  missing**; our fetch script skips recordings with no length so every cached
  track has a valid duration.
- Very short recordings (skits/intros under 45s) are filtered out at generation
  time because they are not meaningful for the stop-time fraud signals.
- We do **not** use real play counts, popularity, or any per-user data from
  MusicBrainz — none exists there. All listening behavior is synthetic.
- Catalog target is 500 tracks across ~60 artists; the actual run yielded
  **500 tracks / 57 artists** (a few seed artists returned fewer usable tracks).

## Replay / reproducibility
- The catalog is fetched **once** and cached to `data/catalog.json`. The
  producer/generator and the Kafka replay **never call MusicBrainz live**, so
  the pipeline is fully reproducible and runnable offline.
- `src/generate_events.py --seed 7` deterministically produces a
  **byte-identical** `data/play_events.jsonl` (~45k events) on every run.
- `src/replay_to_kafka.py` streams that file into the `play-events` Kafka topic,
  keyed by `listener_id`, and can be re-run to replay the identical stream.

## Classification
- **Catalog fetch:** batch / one-time.
- **Event stream:** replay of a pre-generated file into Kafka (the streaming
  layer). Batch-generated, streamed on replay — a hybrid path.
